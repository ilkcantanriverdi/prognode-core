# PROGNODE Core ↔ Mobile V0.5.7 — Offline Device ACK + Escalating Audio

**Basis:** User-tested QR works against RC6.4.7 HF4.1. The latest Core source supplied to the mobile team still requires `X-PROGNODE-Session` on `POST /api/mobile/v2/alarms/{occurrenceId}/ack` and does not expose `GET /api/mobile/v2/device/access` or `GET /api/mobile/v2/alerts/pending`. QR pairing alone authenticates a DEVICE, not a human. **No Internet is needed for existing Core-local email/password login**; the repeated sign-in is a local authorization UX problem, not a cloud dependency.

## P0 — Remove repeat login safely (Core must implement)

- Admin UI **Ayarlar → Bağlı mobil cihazlar**: name suggested by OS but editable; unique immutable `deviceId/clientId` and public key; show last-seen, site, **Alarm görüntüle**, **Bu cihazdan ACK ver**, revoke and optional user/PIN requirement. Explicitly grant ACK; no automatic ACK privilege merely because a QR was scanned. Keep default existing user-session mode for old pairings.
- On administrator approval, create scoped **device-bound** read/ACK authority associated with the QR-paired public key/token hash. Validate Core-side **every** ACK; revocation must take effect immediately. Store token on Android Keystore/iOS Keychain, rotate on re-pair and invalidate on lost/stolen device. Do not rely on a human-editable phone name as identity.
- `GET /api/mobile/v2/device/access` over pinned LAN HTTPS, bearer paired-client token: `{deviceId,displayName,canViewAlarms,canAcknowledge,ackAuthMode:"DEVICE"|"USER_SESSION"|"PIN_OR_BIOMETRIC",requiresUserLogin,grantedBy,lastUpdatedUtc}`. Return truthful state; do not return credentials. Authenticated pairing does not mean ACK permission.
- `POST /api/mobile/v2/alarms/{occurrenceId}/ack`: accept `(valid device bearer AND server-side current device ACK grant)` **OR** current signed Core user session. For device grant do not require `X-PROGNODE-Session`; user-session mode still requires it. Responses: `200 {acknowledged:true,occurrenceId}` after actual Core transaction, `401 ACK_USER_AUTH_REQUIRED` if mode requires a user, `403 ACK_FORBIDDEN` if revoked/no grant, `409 STALE_OCCURRENCE` when old occurrence; never ACK an alarm restarted since the phone notification. Audit `serverId,occurrenceId,deviceId,principal (DEVICE:<id> vs USER:<id>),result,timestamp`. Idempotent repeat ACK; do not clear PLC process condition.
- Shared shift phones: site may require a **Core-verified operator PIN** for personal attribution before ACK. Device-only ACK is audited as DEVICE, never misattributed to the operator. No anonymous ACK; no hidden cloud login.

## P0 — Core remains the owner of the repeat obligation

- Existing `AlarmNotificationMode.RepeatUntilAcknowledged` and `RepeatIntervalSeconds` already generate persisted `ACTIVE` and `REMINDER` with common `occurrenceId` while condition is active. Expose selected alarm policy on `GET /api/mobile/v2/alerts/pending`, scoped to the authenticated paired device even when ACK requires a separate human session. `404` on older Core is NOT an empty pending set. Suggested response `{schemaVersion:1,items:[{occurrenceId,profile:"ACK_REMINDER"|"CRITICAL_ACK",profileRevision,reminderIntervalSec,repeatAudioWindowMin,activeAtUtc,title,message,sourceName,severity}]}`.
- Keep selected alarm rules, profile and pending ACK across Core restart; unacknowledged occurrences remain pending after process CLEAR **only** when `ContinueAfterClearUntilAcknowledged` is configured. ACK by any authorized user/device stops Core reminders and emits ACK event for other devices. On connection loss Core must not claim phone received/did not receive or that ACK succeeded.
- For QR-only paired read/view clients, do **not** require an ACK session to fetch their scoped repeat profiles. Reading alarm policy grants no ACK authorization. Never silently apply repeating phone audio to **all** severity=Critical alarms.
- Settings: **Bir kez bildir** vs **ACK edilene kadar tekrarla**, 60 s example cadence, priority and optional site escalation to second operator after 2 min/shift lead after 5 min. This is app alerting, NOT a GSM call.

## Mobile beta in this package (implemented, NOT complete end-to-end)

- A **new Android notification channel** `prognode_ack_repeat_v1` with a royalty-free 7.2-second alarm tone and patterned vibration; Core-selected ACTIVE/REMINDER events with `requiresAcknowledgement=true` use it, updating the SAME occurrence notification ID. Adding new channel is necessary because Android 8+ cannot change an old channel's sound/vibration programmatically. User can disable/change this channel in Android settings; Android OS may rate-limit repeats or suppress via DND/permissions.
- Existing Android foreground LAN poll consumes Core `REMINDER` events; Android release must declare `VIBRATE` and include the WAV raw resource. Even while paired without a login, app may show scoped pending profiles when a new Core implements them. **Do not remove device ACK authorization check in app**; current HF4.1 returns 404 and requires user session for ACK. No unconditional ACK in this mobile build.
- 7.2 seconds of sound **per received Core reminder** is not continuous siren playback and not guaranteed when Android suppresses the app. Core still needs pending state, explicit device grant and phone/device delivery auditing. A later opt-in locally bounded attention mode (max 10 min) may be tested only with Android 16 physical device, observable stop on ACK/revoke/snooze, and Play foreground-service policy review. No indefinite, unavoidable, or silent system override.
- iOS fully offline LAN while suspended/terminated cannot guarantee alert delivery; Internet/APNs needed for remote background push. Critical Alerts need Apple approval, never claim pre-approved.

## Physical release gates

1. Clean QR pair without login: read-only alarms work, ACK unavailable until admin grants device permission. No Internet on either PC/phone, same LAN.
2. Admin explicitly grants DEVICE ACK: no repeated email/password; ACK from detail and notification works, Core audit principal is DEVICE ID; 401/403 after revoke, 409 old notification after clear/reactivation.
3. Set a test alarm to RepeatUntilAcknowledged; trigger with external simulator, check Core journal's successive REMINDERs and same occurrenceId. Observe **new** Android channel's sound/vibration with screen on, screen locked and foreground service running.
4. ACK from a different authorized device stops repeat on all phones on their next confirmed sync. Wi-Fi cut/reconnect: old events only in history, no delayed sound flood or false ACK.
5. Show channel settings/test sound and foreground-service health. Test Samsung One UI 8.5 Doze, OS battery restrictions, no notification permission and DND; record actual latency/failures.
6. Preserve appId `io.prognode.prognode_mobile`, GitHub signed-update workflow, keystore, pinning, original user-session ACK fallback and customer historian/trends/licensing. **No production-release claim before compiled APK and real-device checks.**
